# 监管资料检索与入库协议

> Status: ACTIVE PROCESS GATE  
> Applies to: V2-B 及后续监管知识扩充  
> Date: 2026-09-18  
> Owner: Project

## 1. 为什么新增这份协议

V2 前期的监管知识检索过度集中在“现行食品补充检验方法数据库 / Method→Substance”一侧，并大量沿用仓库中已经出现的术语和文件名进行搜索。这样做能够核验“某方法能检测什么”，但容易漏掉真正决定“为什么这个页面宣传值得关注某类物质”的上游监管资料。

本轮 V2-B 重新检索后发现，市场监管总局现存的历史中央专项整治材料中已经明确给出多组“声称类别→重点检验成分”的抽检/风险监测关系；2023—2026 年又存在新的保健功能目录、执法案例、非食用物质名录、执法检验方法和补充检验方法，可用于校正历史关系的当前适用边界。

因此，以后不得仅以“当前补充检验方法数据库里是否出现某物质”作为监管知识检索是否完成的判断。

## 2. 强制检索层级

每一个拟新增的监管关注方向，至少按以下层级检索并记录结果：

1. **当前中央正式监管文件**
   - 国家市场监督管理总局（SAMR）
   - 国家卫生健康委员会（NHC）
   - 必要时国家药监局（NMPA）
   - 重点找：非食用物质名录、公告、通知、有毒有害认定、执法检验方法、专项行动文件。
2. **当前保健食品功能目录及新旧功能名称对应关系**
   - 用于统一页面宣传词、历史声称名称和当前官方功能名称。
3. **当前食品补充检验方法数据库 / 快速检测方法 / 国家标准**
   - 用于回答“如何检测”，不得反向推出 Claim→Substance。
4. **历史中央专项整治、监督抽检、风险监测资料**
   - 重点查找“类别、声称类别、检验项目（检测成分）”等表格。
   - 历史资料可作为抽检筛查知识来源，但必须显式标记 historical，不得伪装为当前法定抽检要求。
5. **当前中央或省级官方执法案例**
   - 用于交叉验证某类宣传与实际查处物质之间仍存在监管现实关联。
   - 个案不能单独证明整个类别必然对应某物质。
6. **地方监管部门正式资料**
   - 仅在中央资料不足时补充；必须保留地域和时间边界。
7. **论文、行业文章、新闻转载**
   - 只能作为线索来源，不得直接进入 verified Reference。

## 3. 搜索必须使用“来源原生术语”

不能只搜索项目内部术语，如 `Risk→Substance`、`mapping`、`页面宣传线索`。

针对每一个方向，应组合搜索以下原生表达：

- `声称XX功能产品`
- `XX类样品`
- `辅助降XX`
- `调节XX`
- 当前保健功能名称，例如 `有助于维持血压健康水平`
- `检验项目（检测成分）`
- `监督抽检`
- `风险监测`
- `非法添加`
- `非食用物质名录`
- `执法检验方法`
- `有毒有害认定`
- `食品补充检验方法`
- `典型案例`

例如血压方向不能只搜“氨氯地平 检验方法”，还应搜：

`声称辅助降血压 + 检验项目`、`调节血压 + 风险监测`、`降压 + 食品 + 非法添加 + 典型案例`、`降压药物 + 食品补充检验方法`。

## 4. 同一功能必须做“新旧名称”双向检索

2023 年保健食品功能目录调整后，多个历史名称已经规范为新的声称名称。检索必须同时覆盖历史和当前名称，例如：

- `改善睡眠` ↔ `有助于改善睡眠`
- `抗疲劳` / `缓解体力疲劳` ↔ `缓解体力疲劳`
- `减肥` ↔ `有助于控制体内脂肪`
- `调节血脂` / `辅助降血脂` ↔ `有助于维持血脂健康水平`
- `调节血糖` / `辅助降血糖` ↔ `有助于维持血糖健康水平`
- `调节血压` / `辅助降血压` ↔ `有助于维持血压健康水平`

## 5. 时间状态与证据强度分开

每条关系至少记录：

- `source_date`
- `temporal_status`: `current | historical`
- `basis_type`
- `product_scope`
- `source_basis_text`

禁止把“历史中央抽检计划”改写成“当前强制抽检要求”。

同时也禁止因为资料是 historical 就直接丢弃。历史中央抽检/风险监测资料可以证明当时监管系统明确采用过某种“声称类别→检验项目”筛查关系；是否进入当前产品 Recommendation，要再结合当前来源、方法生命周期和 UI 边界决定。

## 6. 三角验证门槛

对于拟进入生产 Recommendation 的新方向，优先满足以下三类证据中的至少两类：

1. **场景证据**：官方文件明确把某声称/产品类别与某物质或检测项目关联；
2. **当前监管证据**：当前名录、通知、执法认定或近期官方案例仍支持该方向；
3. **检测证据**：存在当前可用、来源明确的检验方法，并已治理适用范围。

若只有第 3 类“方法能检测某物质”，不得建立 Claim→Risk→Substance。

## 7. 方法库检索不能只查已有 7 个方法

截至 2026-06，市场监管总局公开说明累计已发布 112 项食品补充检验方法。项目当前 `inspection_reference.json` 仅是一个经过深度整理的子集，不代表方法全集。

V2-B 每增加一个监管方向，都必须重新检查官方补充检验方法数据库，而不是只在当前仓库的 7 个方法中找答案。

优先检查：

- 方法名称与编号
- lifecycle/current 状态
- 目标物列表
- 产品/基质/剂型适用范围
- 是否定性、定量或快速筛查
- 是否存在替代/废止关系
- 是否属于补充检验、快速检测、国家标准或执法检验方法

## 8. 入库边界

### 可以进入 verified Risk Reference

- 官方来源直接支持的“声称/产品场景→具体物质/物质组”关系；
- 时间、产品范围、原文依据均可追溯；
- 不依赖药理常识反推。

### 只能进入 Method Reference

- 官方方法明确能检测某物质，但没有找到该宣传场景与物质的监管关联。

### 只能保留为研究候选

- 论文/行业资料；
- 仅凭药理学推断；
- 仅凭物质名称与宣传语义相似；
- 无法定位正式来源正文。

## 9. 特殊例外必须显式记录

例如褪黑素：历史“改善睡眠”抽检表中曾作为检测项目出现，但当前又是合法保健食品原料，并有现行 `GB/T 45443-2025` 测定标准。因此不能把 `睡眠宣传→褪黑素` 简化成“疑似非法添加褪黑素”。必须结合保健食品身份、注册/备案、配料和产品上下文单独处理。

类似例外不得隐藏在代码注释里，应进入治理文档和测试。

## 10. V2-B 执行清单

每个方向完成前必须回答：

- [ ] 当前官方功能名称是什么？历史同义名称是什么？
- [ ] 是否存在官方“声称类别→检验项目/物质”资料？
- [ ] 该资料是 current 还是 historical？
- [ ] 是否有近年官方名录/通知/案例进行交叉验证？
- [ ] 当前官方方法数据库有哪些直接相关方法？
- [ ] 项目当前知识库已经收录哪些、漏了哪些？
- [ ] 哪些页面表达可以触发 Recommendation，哪些只能作为 Claim？
- [ ] 是否存在合法原料/合法药食同源/保健食品身份等反例？
- [ ] Product Context 对方法适用性有什么要求？
- [ ] UI 是否明确“不代表实际含有/违法”？

只有清单完成后，才允许修改生产 Claim→Inspection Bridge。
