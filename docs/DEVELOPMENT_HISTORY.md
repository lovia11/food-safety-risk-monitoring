# 项目开发与决策历史

本文不是 Changelog。它记录项目为什么采用当前技术路线、真实验证过什么、在哪些地方失败过，以及后续开发不能遗忘的边界。内容依据 Git history、稳定 tag、当前代码与测试、`collection_experiment.md`、`docs/output_inventory.md` 和保留的真实 `output/<run_id>` 整理。

为避免把实现和验收混在一起，本文使用以下口径：

- **真实淘宝验证**：存在真实页面运行目录、日志和结果文件；
- **Web 真实 E2E**：任务由 Web API 创建，并真实完成淘宝到 Web 结果闭环；
- **离线验证**：自动化测试、保存的真实 fixture 或历史 run 重建，不在该次测试中访问淘宝；
- **实现但未充分真实验证**：代码存在、离线测试通过，但页面模板或规模覆盖不足；
- **证据不足**：当前仓库无法证明，不补写故事；
- **规划**：需求尚未实现。

## 1. 项目背景与业务问题

### 1.1 项目来源

这是一个本科毕业设计项目。仓库能够确认的主题是：面向淘宝的食药同源与保健食品风险线索发现和辅助筛查。当前仓库没有能够证明某个市场监管机构正式立项、委托或上线使用的材料，因此文档不写具体使用单位，也不把概念 UI 中曾出现的机构名称视为真实项目背景。

### 1.2 希望解决的问题

淘宝商品的宣传信息并不只在标题中。功效相关表达可能出现在长详情图、正文、用户评价或问答里。人工逐个搜索、打开、滚动、保存图片、识别文字并整理证据，工作重复且难以形成统一、可追溯的记录。

本项目尝试把以下前置筛查工作串起来：

1. 按食药同源对象或相关商品表达在淘宝发现候选；
2. 保存商品身份、店铺、页面链接和检索来源；
3. 进入当前商品详情，保存正文、原始图片、页面截图和采集元数据；
4. 对图片执行 OCR；
5. 用透明、可配置的规则寻找功效表达；
6. 保存原文、来源、路径和行号，形成 Evidence；
7. 由人工复核，而不是由程序给出执法结论。

### 1.3 为什么当前选择淘宝

淘宝是本毕设明确指定的当前目标平台，真实搜索页能提供大量食药同源相关商品，商品详情又包含大量图片化宣传信息，适合验证“搜索—详情—OCR—证据”的完整问题链。当前代码只实现淘宝/天猫页面适配，不能由此声称系统已具备通用电商平台能力。

### 1.4 为什么是“风险线索发现”，不是“非法添加检测”

网页内容最多证明某段文字或图片曾在采集时出现在页面上。它不能证明商品实际成分，也不能独立完成法律定性。OCR 还可能误识别，用户评价也不等于商家承诺，规则命中更不等于功效真实或违法。

因此系统的正确业务位置是：从大批页面中缩小人工检查范围，提供可追溯线索。实际非法添加需要抽样、实验室检验和规范的证据链；违法或虚假宣传认定还需要页面语境、主体、资质、产品类别和适用法规等信息。当前项目均不替代这些工作。

## 2. 项目目标与边界

### 2.1 当前能够完成的工作

- 在普通本地终端中独立启动可见 Chrome；
- 在项目浏览器中复用淘宝登录状态，必要时等待人工登录/验证；
- 执行一个关键词的 Quick Task，或按 MonitorTarget 执行多个 SearchQuery；
- 解析真实搜索卡片、按商品 ID 去重并保存 Search Diagnostics；
- 打开有限数量的详情页，滚动到当前商品图文详情边界；
- 以 DOM 归属为主保存当前商品详情原图，并保存 Network 与 Screenshot 证据；
- 使用 PaddleOCR 识别筛选后的详情图；
- 用本地配置词库发现功效表达，区分商家管理内容、用户生成内容和被排除的其他商品推荐；
- 输出 Evidence、批次 JSON/CSV/Markdown、日志和 Web Snapshot；
- 通过 Web 创建/轮询/恢复任务、查看商品和证据、保存人工复核状态；
- 使用 SQLite 跨 run 查询商品快照，同时保留文件系统原始证据。

### 2.2 当前不能完成的工作

- 从页面判断食品真实成分或检出药物；
- 自动判断商品违法、功效真实或处罚结论；
- 自动解决淘宝滑块、验证码或其他安全控制；
- 保证淘宝页面结构变化后仍无需维护；
- 保证无人值守、大规模、长期连续或并发采集；
- 提供官方完整的食药同源对象与搜索词目录；
- 将当前搜索卡片地区解释为商品产地或卖家注册地；
- 提供正式多用户、权限、审核流和审计系统。

### 2.3 页面证据与实验室检测的边界

系统保存的标题、DOM、图片、OCR、截图和 URL 是“网络页面证据”。它们可以支持“页面出现了什么表达”的人工判断。实验室检测回答的是“样品中实际有什么成分”。二者不能互相替代，也不能由前者推断后者。

## 3. 总体技术路线是如何形成的

项目不是先设计完整架构再一次实现，而是沿着真实页面的不确定性逐层形成：

1. **先证明详情内容能被可靠定位。** 早期用真实已登录浏览器侦察一个商品，发现长详情图适合以 DOM 容器归属，而不是从全部 Network 图片中猜测。
2. **再证明图片能进入本地分析。** 保存原始响应、校验实际 MIME 和尺寸，对宣传图执行 PaddleOCR。
3. **把文字变成可解释线索。** 合并标题、当前商品 DOM 和 OCR；同时发现用户评价、问答和推荐商品会造成归因错误，于是引入 `content_origin` 与推荐区排除。
4. **从单商品扩到候选批次。** 解析真实搜索页，按商品 ID 去重，建立逐商品状态、失败隔离、重试和断点。
5. **从调试工具迁移到 standalone。** Codex Browser 只保留为页面侦察工具；最终采集由 Python + Playwright + 项目 Chrome 自己运行。
6. **为外部页面变化增加可观察性。** Search Diagnostics 记录停止原因、字段缺失和 Selector Health；详情保存 DOM、Network、截图和滚动状态。
7. **从命令行进入任务系统。** Web 通过后台线程调用同一 Pipeline，轮询 `web_snapshot.json`，避免复制采集逻辑。
8. **从单 run 展示进入跨 run 数据。** SQLite 索引 Task、ProductSnapshot、Evidence 和 Review，原始大文件仍留在 `output`。
9. **从单关键词进入监测对象。** MonitorTarget 组织多个 SearchQuery，CandidateHit 保留召回来源，跨 Query 去重后继续复用冻结 Collector。

最终形成的主路线是：

```text
MonitorTarget / Quick keyword
  → SearchQuery
  → CandidateHit / 去重候选
  → 商品详情 DOM + Network + Screenshot
  → 详情原图
  → PaddleOCR
  → 来源感知的功效规则
  → Evidence
  → 人工复核
  → output + SQLite + Web
```

每一层解决的是前一阶段真实暴露的问题，而不是为了增加模块数量。

## 4. 早期技术验证阶段

### 4.1 单商品页面侦察：`20260817T171318`

最早保留的完整侦察对象是商品 `606232126144`。`collection_experiment.md` 明确说明，这一阶段借助 Codex 浏览器调试能力观察真实页面，因此属于“页面侦察与方法验证”，**不是**关闭 Codex 后 standalone Playwright 已验收的证明。

当时在可见、已登录 Chrome 中实际观察到：

- 详情页签区域：`#titleTabs`；
- 图文详情正文：`#imageTextInfo-container`；
- 详情图片使用动态 class，因此不能把某个完整 hash class 当成长期稳定选择器；
- 点击图文详情后正文容器高度约 23,083 px；
- 页面最终高度会因底部推荐等动态内容从约 25,818 px 增长到约 28,145 px。

同一个页面上共观察到 50 个 `<img>`、22 个 CSS 背景和 108 个唯一图片资源。正文 DOM 精确关联 17 张图片，且 17/17 能从观察资源中匹配并保存；其余 91 个 Network/资源图片包含主图、SKU、推荐、头像、Logo 和平台资源。这个比例直接说明：**Network 很适合拿原始响应，但不能单独判断图片属于当前商品详情。**

17 张正文图中，人工抽查又发现 2 张不适合 OCR：一张关联商品九宫格和一张平台价格说明。因此最初 OCR 候选集中在正文宣传/包装图，而不是把所有网页图片无差别识别。

另一个重要发现是 URL 扩展名不可靠：16 个以 `.jpg` 结尾的 URL 实际响应 MIME 是 WebP。后续实现因此以响应 MIME 和 Pillow 解析结果决定文件扩展名并校验图片，而不是相信 URL 后缀。

当时保存了 1 张概览、6 张分段和 1 张全页截图。截图能证明页面上下文，但包含页头、页签、悬浮栏、缩放文字和推荐区，不适合作为主要 OCR 输入。由此形成三种获取方式的明确分工：

- DOM：判断内容是否属于当前商品；
- Network：获得未被页面缩放的原始响应并补取；
- Screenshot：人工复核上下文和失败留证。

该阶段还记录了环境问题：本机代理/TLS 曾阻止从 PyPI 安装 Playwright。这个问题说明“页面方法可行”和“项目独立环境已可运行”是两件事，所以报告后来补上 standalone 限定说明。

### 4.2 OCR 与规则实验

早期商品原图进入 PaddleOCR 后，OCR 文本能识别出“深夜难眠”“整夜辗转反侧”“夜里多梦”等详情图表达。Phase 3 逐渐把标题、DOM 和 OCR 合并，并为每条命中保存功效分类、原文、命中词、来源文件和行号。

很快又发现两个归因问题：

1. DOM 中的用户评价和问答可能含“睡眠”“失眠”等词，但不等于商家承诺；
2. 页面尾部“本店推荐”中的其他商品标题会把别的商品宣传误算到当前商品。

因此 `phase3_analysis.py` 增加 `seller_managed`、`user_generated` 和 `excluded_other_product`。推荐区从最后一个可信“本店推荐”边界后排除；用户内容可以触发辅助复核线索，但报告必须明确其来源。

### 4.3 从单商品到批次：`20260817T181659_batch`

早期批次保留 20 个真实候选，其中 2 件商品具有详情、OCR、分析和 Evidence，其余保持待详情状态。该 run 证明批次状态和“部分成功、其余不伪造”的输出方式，但其搜索来源是此前保存/准备的真实数据，不能当作实时自动搜索完整验收。

### 4.4 standalone 迁移与 2026-08-28 调试

项目随后把浏览器侦察结果迁入 Python + Playwright。目标变为：即使关闭 Codex，用户在普通终端运行代码也能独立打开浏览器并完成搜索、详情、图片、OCR 和结果保存。

这一迁移并非一次成功。保留的 `20260828_live_smoke*` 显示，早期运行有时搜索页连续只能提取 0 张卡片；`live_smoke4`、`live_direct1/2` 又明确检测到淘宝登录。`20260828_user_smoke1` 开始先访问淘宝首页建立正常会话，但首页/搜索仍出现人工验证。随后切换到项目自己启动 Chrome 并通过 CDP 连接，`20260828_cdp_smoke1` 仍经历人工验证与 0 卡片尝试。

最终 `20260828_cdp_smoke2` 完成 46 个去重搜索商品、选择 10 件并完成 10 件详情，共保存 176 张原图。后续 OCR 由用户在证明链路可行后停止，只有 1 件进入完整分析，因此这个 run 证明的是“10 件详情采集”和“至少 1 件端到端”，不能写成“10 件全部分析”。

这段调试历史是当前浏览器策略的重要来源：使用项目专用 `.browser-profile`，默认可见 Chrome/CDP；先进入淘宝首页，再从可见搜索框提交；遇到登录/验证只暂停等待人工；日志区分平台阻塞、页面结构异常和浏览器被用户关闭产生的次生错误。

## 5. Collector Baseline v0.2

Tag：`collector-baseline-v0.2`

Commit：`3c77b795332f5e961d1c28a74cfd82caf37760e7`

提交时间：2026-09-01 23:59:26 +08:00
离线测试：48 项

### 5.1 当时要解决的核心问题

早期系统已经“有时能跑”，但还缺少可回归的 Collector 边界。v0.2 的目标不是增加业务页面，而是把最脆弱的真实淘宝链稳定成基线：

- 浏览器如何启动和保存独立登录状态；
- 搜索如何走正常首页交互而不是高风险接口猜测；
- 候选和详情数量如何分离；
- 页面结构变化如何留下诊断；
- 详情何时停止滚动；
- 一个商品失败是否会破坏整批；
- 中断后怎样保留已完成工作；
- 完整 Pipeline 是否仍可执行 OCR、规则和 Evidence。

### 5.2 为什么拆分 `candidate_limit` 与 `detail_limit`

搜索候选提取相对快，详情打开、图片下载和尤其 CPU OCR 成本高。如果只有一个 `limit`，就无法同时测试较大搜索范围和很小的高成本详情范围。

拆分后：

- `candidate_limit` 表示最多保留多少个去重候选；
- `detail_limit` 表示其中前多少个进入详情/OCR主链；
- 没进入详情的候选保留 `pending_detail_collection`，不能生成假 OCR/分析结果；
- 旧 `--limit` 仅作为兼容别名保留。

这使 `test_b` 能请求 50 个候选但只采 5 件详情，也使完整 E2E 能用 10 候选、2 详情控制成本。

### 5.3 Search Diagnostics 与 Selector Health

淘宝搜索页是外部动态页面，只看“结果为空”无法区分登录、验证、DOM 变化、滚动停滞或真实数量不足。v0.2 为每次搜索保存：

- 请求候选数、实际去重候选数和进入详情数；
- 滚动次数、耗时和明确停止原因；
- 标题、店铺、地区等字段缺失数；
- Selector Health 覆盖率；
- 失败类型和错误消息；
- 页面 HTML、截图和滚动状态。

Selector Health 的职责是告警，不会在发现覆盖率下降后自动猜新选择器。自动替换可能静默抓错字段，比明确失败更危险。

### 5.4 详情滚动基线

固定滚到 70% 或 80% 曾被考虑，但 10 件真实详情的最后一张详情图大约分布在整页 26%—88%。固定百分比既可能越过正文进入推荐区，也可能漏掉特别长的详情。

最终以 `#imageTextInfo-container` 为权威边界，同时观察详情图片总数、已加载数、URL 数、详情容器底部和页面高度。视口到达详情底部且内容连续稳定后停止。找不到容器时才依次使用推荐区边界、页面底部、92% 页面比例和滚动位置不变作为兜底，并始终保留最大滚动次数。

后续真实 run 中，v0.2 E2E、v0.3 Web E2E 和 v0.5 Monitor E2E 的 6 件详情均记录为 `detail_container_stable`，证明主路径已经在这些样本上真实运行；兜底模板仍属于覆盖不足区域。

### 5.5 真实测试 A、B

`20260901_collector_v02_test_a_retry1`：

- `candidate_limit=20`、`detail_limit=3`；
- 实际保留 20 候选；
- 完成 3 件详情、44 张原图；
- 使用 `--skip-ocr`，不属于完整 E2E。

`20260901_collector_v02_test_b`：

- 请求 `candidate_limit=50`、`detail_limit=5`；
- 搜索页实际提取 46 个去重候选，滚动 5 次后连续无新增，以 `stagnant_no_new_products` 停止；
- 标题、店铺、地区覆盖率均为 100%；
- 完成 5 件详情、76 张原图；
- 第 1 件广告跳转首次 `ERR_CONNECTION_TIMED_OUT`，单商品第二次尝试成功；
- 使用 `--skip-ocr`，不能用于证明 OCR/分析。

这说明 Collector 能保留真实数量而不是为了满足 limit 伪造候选，也说明有限重试能处理一次瞬时跳转失败。

### 5.6 v0.2 完整验收

### 5.7 为什么冻结、为什么没有继续做 100 商品单 Query

v0.2 的验收问题是“Collector 改动后最小完整 Pipeline 是否仍成立”，而不是证明规模上限。一个完整 E2E 已覆盖搜索到 Evidence，另一个真实 run 已请求 50 候选并在页面实际 46 个处自然停止。仓库没有 100 商品单 Query 的真实结果，因此项目选择冻结已验证行为，避免把未测试规模写入能力声明。

“继续跑 100 会产生什么结果”当前证据不足。可以确定的是：扩大单 Query 会增加页面滚动、平台风控和后续详情/OCR成本，却不一定增加不同形态商品的覆盖。v0.5 后来用多 Query 扩展发现来源，但这不是 100 商品能力的替代证明。

### 6.1 为什么从命令行进入 Web 任务运行

v0.2 的 Web 只是读取结果。演示时仍要在终端手工运行 Pipeline，再让页面读取某个固定 run，这不是真正的软件闭环。v0.3 的目标是让用户在采集任务页输入参数，由 Web 创建任务、后台运行现有 Pipeline、持续显示状态，并在完成后自动显示新商品。

核心原则是包装稳定 Pipeline，而不是从 Web 再实现一套 Collector/OCR/Analysis。

### 6.2 为什么复用 `ThreadingHTTPServer`

当时 `src/local_api.py` 已能安全提供静态页面和 run 文件。需求只有本机单用户、普通 HTTP 轮询和一个活动任务，没有异步高并发、认证或复杂路由需求。

选择标准库 `ThreadingHTTPServer` 的收益是：

- 不新增 Flask/FastAPI 依赖；
- 不重写已可用的静态/文件服务；
- API 与前端变化可小步完成；
- 长任务交给后台线程，HTTP 请求本身仍快速返回。

代价是它只适合当前单进程 MVP。未来若需要多用户、多进程、认证或任务队列，才有充分理由重新评估框架。

### 6.3 后台线程、单活动任务和 409

`TaskManager` 在进程内维护一个 worker thread。创建任务后立即返回 HTTP 202，后台同步调用 `StandalonePipeline`；前端轮询 `web_snapshot.json`。

浏览器 profile、Chrome 调试端口和 CPU OCR 都是共享资源。第一版不具备隔离条件，因此第二个任务不是排队，而是返回 HTTP 409 和当前 `activeTaskId`。这个保护比“看似支持并发但相互破坏”更可靠。

### 6.4 Windows 原子写问题

任务执行时 Pipeline 会持续更新 `batch_state.json` 和 `web_snapshot.json`，Web 又会同时读取。直接覆盖文件可能让前端读到半截 JSON。v0.3 改为：先写同目录临时文件，再 `replace` 目标文件。

Windows 上 HTTP 读取可能短暂锁住目标文件，因此 `src/runtime.py` 对 `PermissionError` 做 20 次、每次 10 ms 的有限重试。这个逻辑不是性能优化，而是保证状态快照完整性的兼容处理。它不能被简单改回普通 `write_text`。

### 6.5 清除前端硬编码

前端以前依赖固定 run ID/历史商品。v0.3 后改为从 `/api/tasks` 和 run 快照发现最新任务；活动任务轮询完成后自动刷新商品和详情。固定历史数据只保留为输出证据，不再决定页面当前任务。

### 6.6 v0.3 Web 真实 E2E

`20260902T005526_task` 是由 Web 创建的真实任务，运行于 00:55:26—01:07:15，约 11 分 49 秒：

- 关键词酸枣仁，10 候选、2 详情；
- 37 张原图、30 张 OCR 成功图；
- 2 件完成助眠规则分析并产生 Evidence；
- 0 最终失败；
- Web 状态从搜索、详情、OCR/分析更新到完成；
- 新任务商品自动进入商品监测和风险研判。

### 6.7 v0.3 留下的限制

- 单机、单用户、单活动任务；
- 后台 daemon thread 不等于持久任务队列；
- 没有取消接口；
- 人工验证仍需要在浏览器处理并回到服务终端按 Enter；
- 任务和商品主要按每个 run 的文件组织，跨 run 查询与人工复核还不方便。

### 7.1 为什么只有文件系统已经不够

`output/<run_id>` 很适合保存原始证据，却不适合回答跨任务业务问题：同一商品采过几次、哪一次命中了什么、哪些待复核、用户保存的复核备注是什么。让前端每次遍历大量 JSON 也会把数据兼容逻辑散落到 UI。

另一方面，直接把所有大文件迁入数据库会削弱可检查性并造成大重构。v0.4 因此采用“双层存储”：文件系统继续保存运行事实，SQLite 只建立业务索引和可变人工状态。

### 7.2 Task → ProductSnapshot → Product

模型区分“商品身份”和“某次页面状态”：

- `Task`：一次采集运行；
- `Product`：以淘宝商品 ID 标识的稳定对象；
- `ProductSnapshot`：某个 Task 中某 Product 的标题、店铺、地区、采集状态、分析结果和文件路径。

同一个 Product 在不同时间可能改标题、详情或宣传内容，因此不能把某次 OCR/风险结果永久写到 Product。关系上，一个 Task 有多个 Snapshot，一个 Product 也可以有多个 Snapshot。

### 7.3 为什么 Evidence 和 Review 属于 Snapshot

Evidence 指向某次采集的原文、路径和行号。如果以后页面改变或词库改变，同一商品的 Evidence 也会改变。Review 是人工对这次页面证据的判断，同样不能自动继承为商品永久结论。

所以 Evidence 和 Review 都挂在 ProductSnapshot。当前 Review 只保存最新状态和备注：`pending`、`recommend_follow_up`、`no_further_action`。这是 MVP 级人工闭环，不是正式多级审核流程。

### 7.4 为什么原图/OCR/HTML仍在文件系统

图片、完整 HTML、Network response、OCR 逐图 JSON 和日志体积大、结构多样，而且经常需要直接打开人工核查。把这些内容塞入 SQLite 没有当前业务收益。数据库只保存计数、结构化 Evidence 和相对路径，原始文件仍以 `output` 为证据来源。

### 7.5 历史 run 幂等导入

服务启动时扫描含有效 `web_snapshot.json` 的历史 run 并导入 SQLite。主键和唯一约束保证重复导入不复制 Task、Snapshot 或 Evidence；重新导入更新机器生成字段，但保留人工 Review。

测试还覆盖：

- 同一 Product 在两个任务中形成两个 Snapshot；
- Evidence 来源字段可结构化读取；
- 数据库关闭后用新的 `DataStore` 实例打开，Review 仍存在；
- 重新导入同一 run 不覆盖人工备注；
- 保留的 v0.2/v0.3 真实 run 能建立业务索引。

这里的“重启持久化”有自动化重开数据库实例的直接证据。当前仓库没有单独保留一次人工关闭/重启整个 Web 服务并截图验收的记录，因此不扩大表述。

### 7.6 v0.4 的验收边界

v0.4 没有重写或扩展 Collector，也没有发现一份专门为 v0.4 新跑的真实淘宝 E2E。它以 75 项离线测试、历史真实 run 幂等导入、API 查询和 Review 重开持久化验证数据层。不能把历史 run 的淘宝采集写成 v0.4 新采集。

### 8.1 单关键词模式的业务不足

Quick Task 把用户输入的一个词直接交给淘宝，适合冒烟测试，但一个监测对象可能以原料名、产品形态或组合词出现。只靠单词会把“业务监测对象”和“某次搜索表达”混为一谈，也无法解释某商品是被哪个词召回的。

v0.5 没有追求一次 Query 无限滚动，而是先建立可解释的多 Query 基础。

### 8.2 MonitorTarget

MonitorTarget 表示业务上要监测的标准对象，包含标准名、类型、来源、来源引用、日期和启用状态。当前只有 `酸枣仁` 一个开发种子。

`config/monitor_targets.development.json` 明确标记 `dataset_status=development_seed`，来源引用也写明“完整权威来源待后续单独核验”。它用于工程验收，不能写成官方完整食药同源目录。

### 8.3 SearchQuery

SearchQuery 是 MonitorTarget 下的一条实际淘宝检索表达，含 Query 类型、顺序和启用状态。当前酸枣仁对象有：

1. `酸枣仁`，base；
2. `酸枣仁茶`，product_form。

把 Target 和 Query 分开，未来才能在不改变商品/任务模型的前提下维护召回表达，并解释每次任务的检索策略。

### 8.4 CandidateHit

跨 Query 去重会丢失来源：同一商品可能同时被“酸枣仁”和“酸枣仁茶”召回。如果只保留最终候选，无法回答哪个 Query 命中过、各自排名多少。

CandidateHit 因此记录 `task_id`、`product_id`、`query_id`、`query_text`、rank 和时间。它是发现来源，不是风险 Evidence，也不表示详情已经采集。

### 8.5 为什么多 Query 串行

当前系统只有一个项目浏览器上下文、一个专用 profile 和一个活动任务。并行 Query 会增加页面竞争、平台请求压力和诊断复杂度，而当前每个 Query 首屏即可获得足够候选，没有并行收益证据。

所以按配置 `order` 串行执行。每个 Query 使用独立搜索目录和 Diagnostics，完成后再确定性合并。代价是 Query 多时耗时线性增长；在真实性能数据出现前不提前引入并行。

### 8.6 为什么不重写 LiveSearchCollector

v0.2 已冻结真实验证的单 Query Collector。v0.5 把多 Query 编排放在 `DiscoveryCoordinator`：每次仍调用原 `LiveSearchCollector.collect`，最后写一份兼容 `search/search_candidates.json` 的合并结果。这样降低回归范围，Quick Task 也继续走原路径。

### 8.7 跨 Query 去重和确定性选择

当前规则：

1. Query 按 `order`、再按 `query_id` 排序；
2. Query 内候选保持原排名；
3. 遇到首个有效 `product_id` 时加入合并列表；
4. 后续重复商品不再加入合并列表，但继续保存 CandidateHit；
5. 合并列表重新连续编号；
6. 前 `detail_limit` 个唯一候选进入详情。

该规则容易复现和解释，但不是风险优先、地区均衡或统计抽样。未来改变选择算法必须单独定义目标和评估方法。

### 8.8 v0.5 Monitor Web E2E

第一次预检 `20260902T192644_task` 在 Playwright 创建子进程前遇到 `[WinError 5] 拒绝访问`。错误栈位于 Windows asyncio 创建 pipe，未进入淘宝页面，因此被正确归类为受限执行环境问题，而不是验证码或 Collector 问题。

## 9. 关键技术问题与解决过程

### 9.1 淘宝登录与验证码

#### 问题

浏览器“能打开淘宝”不等于搜索和详情可采集。淘宝可能显示登录页、滑块/人工验证、骨架屏或 0 卡片。用户日常 Chrome 已登录，也不等于项目浏览器已登录，因为项目使用独立 `.browser-profile`。

Chrome 账号登录和淘宝站点登录也是不同概念：项目不需要用户登录 Google/Chrome 账号；它只需要项目 profile 内有效的淘宝会话。

#### 真实尝试

- `live_smoke` 至 `live_smoke3`：页面连续提取 0 卡片；
- `live_smoke4`、`live_direct1/2`：程序检测到淘宝登录；
- `user_smoke1`：改为先访问淘宝首页并由可见搜索框进入，仍遇到人工验证；
- `cdp_smoke1`：CDP 项目浏览器中仍经历验证和 0 卡片；
- 后续 `cdp_smoke2` 及 v0.2/v0.3/v0.5 run 成功。

#### 当前策略

- 默认启动可见 Chrome，并使用项目专用持久 profile；
- 默认 CDP 模式，`persistent` 只保留为兼容/诊断路径；
- 先打开淘宝首页建立正常会话，再从可见输入框搜索；
- 同时检查 iframe、URL、标题和正文中的登录/验证信号；
- 发现阻塞时写 WARNING、更新 Web 为 `manual_action_required`，等待用户在项目浏览器处理并在终端确认；
- 人工处理后再次检测，仍阻塞则明确失败；
- 用户关闭页面导致 `TargetClosedError` 时转成“项目浏览器已关闭”的次生错误，避免误报成验证码根因。

#### 为什么不能绕过

平台验证是访问控制的一部分。项目目标是低频辅助筛查，不需要、也不应实现验证码破解、批量账号或规避风控。当前 CDP 参数测试还明确保证不擅自加入 `AutomationControlled` 等 stealth flag。以后即使技术上可以尝试，也必须先重新确认合规边界，不能作为普通稳定性修复。

### 9.2 网络代理与执行环境

开发机需要代理访问 Codex，但淘宝浏览器未必应走同一代理。当前 `--direct-browser` 只给项目启动的 Chrome 加 `--no-proxy-server`，不修改 Windows、Codex 或其他应用；若淘宝网络必须走代理，可显式关闭 direct 或提供 `--browser-proxy`。

早期 PyPI 安装曾被代理/TLS 阻止；真实详情又出现过广告跳转 `ERR_CONNECTION_TIMED_OUT`。因此网络故障不能一律解释为反爬。

另一个独立问题是受限执行环境可能禁止 Playwright 创建子进程。`20260902T192644_task` 的 `[WinError 5]` 在进入淘宝前发生，普通本地终端重跑成功。诊断顺序必须先看异常位置：如果连 Playwright driver/Chrome 都没启动，就不是淘宝风控。

### 9.3 搜索候选数量

#### 问题与真实观察

早期一个关键词的首屏能看到 46 个唯一卡片。`test_b` 请求 50，但连续 5 次滚动没有新增，最终真实结果仍是 46。limit 是上限，不是必须凑齐的目标。

#### 当前处理

- 商品 ID 去重；
- 卡片重复时只补全已有记录缺失字段；
- 达到 limit、连续无新增、最大滚动、登录/验证、页面结构异常分别记录停止原因；
- Selector Health 记录核心字段覆盖率；
- 候选数量和详情数量分离。

#### 为什么转向多 Query

单 Query 无限滚动不一定增加商品形态覆盖，也不能表达业务对象的多个搜索表达。v0.5 通过 MonitorTarget 下多个 Query 增加可解释的召回来源。当前两 Query 各取 10，产生 20 hits 和 19 unique；这证明多来源机制有效，但不能推导为召回率提升或 100 商品能力。

### 9.4 商品详情滚动与内容边界

#### 问题

淘宝详情页底部常有推荐商品、平台说明和动态区域。滚到整页底部会增加等待、Network 噪声和截图体积，还可能把其他商品当成当前商品。固定 70%/80% 又会因页面模板和详情长度不同而过早或过晚。

#### 被否定的简单方案

- 一律滚到底：会越过当前商品正文；
- 固定 70%/80%：真实 10 商品最后详情图位置约 26%—88%，没有统一安全比例；
- 只看页面高度不变：推荐模块可能动态增长，页面高度不是正文边界。

#### 当前方案

以 `#imageTextInfo-container` 的实际底部为主，并监控图片数、成功加载数、URL 数、容器底部和页面高度。只有到达正文底部且内容连续稳定才停止；容器不存在时才使用推荐标题、整页底部、92%比例或滚动位置不变兜底。`max_scrolls` 防止无限增长。

每个商品写 `scrollStopReason` 和 `scrollStateCount`。v0.2/v0.3/v0.5 完整 E2E 的已处理商品均走 `detail_container_stable`，但其他淘宝模板和所有 fallback 仍需回归。

### 9.5 详情图片获取：DOM / Network / Screenshot

三种来源不是相互替代：

| 来源 | 主要作用 | 主要风险 |
| --- | --- | --- |
| DOM | 确认图片属于当前商品详情，保留顺序、属性、自然尺寸 | DOM/容器会随平台模板变化；懒加载需滚动触发 |
| Network | 保存原始响应、真实 MIME；DOM URL 没捕获时用 Context request 补取 | 噪声极高，单独使用会混入 SKU、推荐、头像、Logo |
| Screenshot | 记录页面上下文、失败状态、人工查看 | 页面缩放、UI 和推荐污染，不适合主要 OCR |

早期单商品的 108 个唯一资源只有 17 个与详情 DOM 精确匹配，是“DOM 定归属、Network 取原图”的最直接依据。当前原图 manifest 还保留 URL、实际 MIME、尺寸、SHA-256 和获取方式，便于审计。

### 9.6 OCR

#### 为什么需要 OCR

大量功效表达位于详情图而非可直接读取的 DOM 文本。只保存图片不做 OCR，规则无法覆盖这部分宣传；对全页截图 OCR 又会混入 UI 和推荐区。

#### 当前实现

- PaddlePaddle 3.2.0 + PaddleOCR 3.x；
- 默认 PP-OCRv6 中文 CPU；
- 依据 `meta.json` 的 OCR 图片编号选择详情原图；
- 每图写纯文本和结构化 JSON，manifest 记录成功、失败、置信度、行数和耗时；
- 低置信度结果仍保留在结构化数据，纯文本按阈值筛选；
- 同一 Pipeline run 复用 OCR runtime，避免每商品重复初始化模型；
- 分析记录 OCR manifest 与规则配置的 SHA-256。

#### 性能与限制

OCR 是当前主要耗时。v0.5 中搜索和两件详情约在 19:30:58 前完成，27 张 OCR 加分析持续到 19:38:31，约 7 分 33 秒。这个数据只代表当时 CPU、图片和模型环境，不是固定基准。

OCR 成功不代表文本全对，也不代表所有页面图片都应进入 OCR。小图、价格说明、平台组件和推荐图需要筛选；图片质量、字体、排版和模型版本都会影响结果。当前没有系统标注集、准确率/召回率或 GPU 性能评估。

### 9.7 用户生成内容与商家内容

淘宝详情 DOM 可能把商品正文、评价、问答和推荐卡片放在同一页面文本中。若只对全部文本做关键词搜索，会发生错误归因。

当前把标题、当前商品 DOM 正文和详情图 OCR 标为 `seller_managed`；评价和问答标为 `user_generated`；推荐区标为 `excluded_other_product`。Evidence 每条保留 `source_type`、`source_label`、`content_origin`、路径和行号。

v0.5 真实商品 `702353081235` 只在 UGC 中命中助眠词，因此风险理由明确写“商品标题、当前商品 DOM 正文及详情图 OCR 未出现同类功效词”。这个例子说明来源字段不是装饰，而是防止把消费者发言写成商家宣传的业务约束。

当前归属仍依赖观察到的 DOM 文本边界和标题标记。页面模板改变后，评价/问答覆盖率不保证完整，需用 fixture 与真实页面共同回归。

### 9.8 风险线索与违法认定边界

规则引擎只执行配置化字面匹配。它擅长解释“哪一行、哪个词、来自哪里”，不擅长理解否定、反讽、暗示或完整法律语境。

因此：

- `detected_effects` 表示配置词库命中；
- `review_required=true` 表示建议人工查看；
- Evidence 是页面原文线索；
- `no_further_action` 是人工复核状态，不是法律结论；
- 报告固定带免责声明；
- UI 不得使用“违法商品”“非法添加已检出”等措辞。

即便标题出现“睡眠”，还需结合产品类别、上下文和资质判断；即便用户说“有效”，也不能推断商家承诺或功效真实。

### 9.9 文件系统与 SQLite

文件系统保留原始证据，优点是可直接打开、便于回放、适合大文件和版本差异；缺点是跨 run 查询与可变人工状态困难。SQLite 提供结构化查询、唯一约束、外键和 Review 持久化；缺点是不能替代大文件证据，schema 也需要维护。

当前分工是：

- `output`：事实主存储；
- SQLite：可重建业务索引 + 人工 Review；
- `web_snapshot.json`：单 run 的前端稳定契约；
- Web API：在这些层之上提供读取与更新入口。

历史 run 幂等导入、人工备注不被重导覆盖，是这套双层存储能够工作的关键。

### 9.10 Web 实时状态与原子写入

长任务不能让创建任务的 HTTP 请求阻塞 10 分钟。后台 worker 运行同步 Pipeline，前端轮询状态。Pipeline 在搜索、详情、OCR/分析和终结阶段持续写 `web_snapshot.json`。

写入必须原子，否则前端可能在文件覆盖中间读取非法 JSON。临时文件 + replace 保证读者只看到旧完整版本或新完整版本；Windows 的短暂锁定用有限重试处理。SQLite 索引同步是 best-effort：文件状态已写成功时，索引失败不应反向破坏采集主链。

这也解释了为什么任务状态仍复用 Web Snapshot，而没有再发明第二套 runtime 状态模型。

## 10. 关键架构决策及其原因

| 问题 | 备选方案 | 最终方案 | 选择原因 | 当前代价 |
| --- | --- | --- | --- | --- |
| 页面访问 | HTTP requests、无头浏览器、可见浏览器 | 项目专用可见 Chrome + Playwright，默认 CDP | 真实页面依赖登录、JS和人工验证；可观察、可接管 | 需要本机 Chrome/profile，受平台页面影响 |
| 登录/验证码 | 自动绕过、复用日常 profile、项目 profile 人工处理 | 项目 profile + 人工处理 | 不绕过平台控制，避免接管用户日常数据 | 不能完全无人值守，需终端确认 |
| 搜索入口 | 直接深链/API猜测、淘宝首页可见搜索 | 首页建立会话后提交搜索框 | 贴近正常访问流程，便于处理登录 | 多一步页面交互，Selector 仍会变化 |
| 详情归属 | 全部 Network、全页截图、DOM | DOM 主归属 + Network 原图 + Screenshot 留证 | 早期 108 资源中只有17个属正文 | 需维护详情容器与模板 |
| 滚动停止 | 整页底部、固定百分比、内容边界 | 详情容器稳定边界优先 | 真实详情结束位置差异大，推荐区噪声多 | fallback 模板覆盖仍有限 |
| OCR | 云 OCR、LLM视觉、本地 PaddleOCR | 本地 PaddleOCR CPU | 可离线、可重复、无外部数据上传，已有真实效果 | 速度慢，复杂版式准确率未量化 |
| 分析 | 黑箱模型、配置化字面规则 | 来源感知的本地规则 | 可解释、可给出逐条 Evidence，适合前期 MVP | 语义能力有限，词库需维护 |
| Pipeline 组织 | Web 重写一套、复用同步 Pipeline | Web Runtime 包装 `StandalonePipeline` | 保护已验证 Collector，避免逻辑分叉 | Runtime 需适配同步长任务 |
| Web Server | Flask/FastAPI、标准库 HTTP | `ThreadingHTTPServer` | 本机单用户需求简单、零新增框架依赖 | 不适合多用户/多进程扩展 |
| 长任务 | HTTP 同步等待、后台 thread、外部队列 | 单后台 thread | 当前最小可靠闭环 | 无持久队列、取消和并发 |
| 实时状态 | 内存、数据库、run JSON | 原子 `web_snapshot.json` +轮询 | 与既有输出契约一致、进度可检查 | 需同步 SQLite 映射 |
| 数据持久化 | 纯文件、纯数据库、双层 | output 原始证据 + SQLite 索引 | 同时满足可追溯和跨 run 查询 | 两层一致性需测试 |
| 复核模型 | Product 永久结论、Snapshot 最新状态、完整审核流 | Snapshot 最新 Review | 页面和判断具有时间性；MVP 范围可控 | 无复核历史、审核人和权限 |
| 多 Query | 并行、串行、重写 Collector | 串行编排并复用 Collector | 降低平台压力与回归范围，顺序可复现 | Query 多时耗时线性增长 |
| 候选选择 | 随机、评分、first-hit | Query 顺序 + Query 内 rank + first-hit | 简单、确定、容易解释 | 不保证代表性、地区平衡或风险优先 |

## 12. 已知限制和技术债

### 12.1 外部页面与采集

- 淘宝 DOM、动态 class、登录策略和风控随时可能变化；
- 当前搜索卡片 Selector 和详情容器来自有限真实样本；
- Selector Health 只能告警，详情模板尚无系统分型；
- fallback 滚动边界没有主路径同等的真实覆盖；
- 广告跳转可能网络超时；重试只能处理部分瞬时问题；
- 普通 Chrome 已登录不能替代项目 profile 登录；
- 没有 100 商品、长期连续或并发验收；
- 当前页面 region 语义只是搜索卡片展示地，无法满足产地分析。

### 12.2 OCR 与分析质量

- CPU OCR 慢，首次模型下载受网络/缓存影响；
- 没有人工标注集和 OCR 准确率指标；
- 图片筛选规则来自有限页面，可能漏掉非典型详情图；
- 字面词规则缺少否定、语境和隐含表达理解；
- 五类词库是开发配置，不是监管标准；
- UGC/商家归属依赖页面结构，模板变化可能影响准确性；
- `review_required` 是规则触发，不是风险等级或违法概率。

### 12.3 Runtime 与 Web

- 进程内 thread/lock 不能跨进程保证唯一任务；
- daemon thread 在服务进程强制退出时不会独立存活；
- 没有任务取消和完整 Session UX；
- 人工验证需要浏览器操作后回终端按 Enter；
- API 无认证，只适合回环地址；
- Product API 无后端分页；
- Web Snapshot 和 SQLite 字段映射需要保持一致；
- 统计页面不能在数据量不足时制造风险率或趋势。

### 12.4 数据与维护

- SQLite 只有轻量 schema 演进，没有正式 migration framework；
- Review 没有历史、审核人、权限和审计日志；
- MonitorTarget 只有开发种子，暂无权威数据导入流程；
- 历史 run 字段版本不同，兼容导入逻辑不能随意删除；
- `output` 未提交 Git，备份和归档策略尚未形成；
- `docs/output_inventory.md` 与 README 部分状态滞后，需要后续独立文档维护轮次更新。

## 14. 对毕业论文和答辩有价值的技术点

### 14.1 可以重点讲的实际贡献

这里更适合称为“项目贡献/工程实现”，不要未经论证写成学术创新：

1. **完整可运行链路。** 从真实淘宝检索到页面原图、OCR、Evidence、人工复核和 Web 展示，不停留在单独爬虫或单张 OCR。
2. **证据可追溯。** 保存原始页面、DOM、Network、截图、图片哈希、OCR文本、规则配置哈希、来源路径和行号。
3. **内容归属意识。** 把当前商品、用户内容和其他商品推荐分开，降低跨商品、跨主体误归因。
4. **外部页面可观察性。** Search Diagnostics、Selector Health、滚动状态和失败分类使页面变化可调试。
5. **稳定核心逐层封装。** v0.2 冻结 Collector，v0.3 在外层做任务化，v0.4 做索引/复核，v0.5 做多 Query 发现，没有为新功能重写已验证主链。
6. **文件证据与业务索引分层。** output 保留原始事实，SQLite 支持跨 run 查询和人工状态。
7. **确定性多 Query 机制。** MonitorTarget、SearchQuery、CandidateHit 分离业务对象、检索表达和召回事实。

### 14.2 可展示的真实数据

答辩展示优先使用：

- v0.5 `20260902T192913_task`：两个 Query、20 hits、19 unique、2 详情、32 原图、27 OCR、8 Evidence；
- 商品 `702353081235`：只有 UGC 助眠线索，展示为什么必须区分来源；
- 商品 `600949052422`：标题/OCR与 UGC 混合线索，展示 Evidence 结构；
- v0.2 `test_b`：请求50、实际46、自然停止和一次重试，展示系统如实记录限制；
- 早期单商品 108 Network 资源仅17个属详情，展示 DOM/Network 分工；
- 81项离线测试与四个稳定 tag，展示工程回归过程。

现场演示应准备历史 run 作为兜底。真实淘宝受登录、网络和风控影响，现场采集失败不等于离线结果页面无法展示；但也不能把历史数据伪装成刚刚实时采集。

### 14.3 容易被问到的问题

#### 为什么不用 requests？

页面依赖登录、JavaScript、动态详情和人工验证。可见浏览器更贴近真实用户流程，也能保存 DOM/Network/截图证据。

#### 为什么不直接抓 Network 所有图片？

早期真实页面有108个唯一资源，只有17个与详情 DOM 匹配。Network 无法单独提供可靠的当前商品归属。

#### 为什么不直接滚到70%或底部？

不同商品详情结束位置差异很大，推荐区还会动态拉长页面。当前使用详情容器稳定边界。

#### 怎么证明不是把其他商品文字算进来？

详情图以 DOM 容器归属；DOM 文本在推荐区边界后排除；Evidence 保留来源类型、路径和行号。

#### 用户评论能算商家宣传吗？

不能自动等同。系统标记为 `user_generated`，只作辅助线索。v0.5 有一件商品的命中全部来自 UGC，可现场说明。

#### 系统能检测非法添加吗？

不能。它只分析网页文字和图片，非法添加必须通过样品和实验室检测。

#### 为什么 SQLite 和文件都要？

原始大文件需要可追溯、可直接核查；SQLite解决跨 run 查询、唯一关系和人工复核状态。数据库可从 output 重建。

#### 多 Query 为什么串行？

当前是单浏览器、单任务、低频采集；串行更可控、诊断更清楚。没有性能数据支持并行。

#### 当前准确率是多少？

没有可报告的准确率。当前缺少人工标注数据集，规则命中只作为候选线索。可以报告真实运行数量和逐条 Evidence，不能编造准确率。

#### 能否稳定抓100件？

当前不能这样宣称。单 Query 最大真实观察为46个去重候选；完整E2E只验证了小批量详情和OCR。

### 14.4 当前不能过度宣称的能力

- 不能称为“自动执法”“违法认定”或“非法添加检测”；
- 不能声称 OCR/规则具有已量化高准确率；
- 不能把 2 件或 10 件样本推成全淘宝代表性结论；
- 不能把 development seed 称为官方目录；
- 不能把搜索卡片 region 称为商品产地；
- 不能把 46 个候选写成平台全部相关商品；
- 不能把跳过 OCR 的测试写成完整端到端；
- 不能把 Codex Browser 辅助侦察写成项目代码独立运行验收；
- 不能把用户评价命中写成商家功效承诺。

## 15. 当前证据缺口说明

为避免未来 AI 自动“补全”历史，明确记录当前没有可靠证据的内容：

- 没有正式监管机构委托、部署或实际执法使用证据；
- 没有 MediaCrawler 代码被接入当前项目的证据；当前 Collector 是本项目实现；
- 没有 100 商品单 Query 或长期无人值守运行证据；
- 没有 OCR、规则或整体系统准确率/召回率评估；
